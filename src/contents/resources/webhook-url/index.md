> **TL;DR** — A webhook URL is an HTTP endpoint you give to another service so it can call you when an event happens, such as a push, a payment, or an alert. It replaces polling with push. Because anyone with the URL can call it, treat the URL as a secret and verify request signatures.

When a commit lands on GitHub, a payment clears in Stripe, or a monitoring tool raises an alert, other systems usually need to react within seconds. Polling each service for changes is slow and wasteful. A webhook URL turns it around: the source service calls your endpoint when the event happens.

This page explains what a webhook URL is, how it compares with polling and regular API calls, and how to receive webhook events in an orchestrated workflow. For hardening an endpoint in depth, see [webhook security best practices](/resources/infrastructure/webhook-security-best-practices).

## How Webhook URLs Work

A webhook URL is a unique, publicly reachable address that receives HTTP requests, usually `POST`. When you register this URL with a third-party service (the webhook provider), that service sends a payload to it whenever a subscribed event happens. [GitHub](https://docs.github.com/en/webhooks/about-webhooks) and [Stripe](https://docs.stripe.com/webhooks) document the pattern for their events.

Key characteristics include:
- **Event-Driven:** Communication is initiated by the source system when an event occurs, not by the receiving system on a schedule.
- **Public HTTP Endpoint:** It's a standard URL that can accept HTTP requests, making it universally compatible with web technologies.
- **One-Way Communication:** The source system sends data (the payload) to the webhook URL but doesn't typically expect a complex response beyond a success/failure status code.

### Webhooks vs. APIs: Pull vs. Push
The fundamental difference between a webhook and a traditional API lies in the direction of communication. With an API, your application actively sends a request to an external service to *pull* data. With a webhook, the external service automatically *pushes* data to your application's URL when an event occurs. This push model removes the need for constant polling.

### Webhooks vs. Polling: Efficiency and Responsiveness
Polling involves repeatedly querying an API endpoint to check for new data. This is inefficient, as most requests return no new information, consuming network bandwidth and API rate limits. Webhooks send data only when there is something new, so they are cheaper and faster.

## Why Webhook Events Need Orchestration

Receiving the request is the easy part. What happens next decides whether the integration is reliable:

- **Data Validation and Transformation:** Incoming payloads must be validated to ensure they conform to the expected schema. Data often needs to be cleaned, enriched, or transformed before it can be used by downstream systems.
- **Security:** A public URL can be called by anyone who has it. Keep the URL secret and authenticate each request, typically with an HMAC signature such as GitHub's [`X-Hub-Signature-256`](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries).
- **Error Handling and Retries:** Downstream systems fail. The processing should retry with backoff and alert someone when retries run out, with the original payload kept for replay.
- **Conditional Logic and Fan-Out:** A single event might need to trigger different workflows based on its content. An orchestrator can route payloads to multiple downstream tasks or systems in parallel, applying conditional logic to decide which actions to take.
- **Observability:** When a webhook-triggered workflow fails, you need to know why. Centralized logging, monitoring, and alerting provide the necessary visibility to debug issues and ensure reliability.

## Orchestrate Webhook Events with Kestra: A Secure Handling Scenario

In Kestra, a [Webhook trigger](/docs/workflow-components/triggers/webhook-trigger) gives a flow its own URL:

`https://{your-kestra-host}/api/v1/{tenant}/executions/webhook/{namespace}/{flowId}/{key}`

In the open-source edition the tenant is `main`. The `key` is part of the URL path and is the endpoint's only built-in check, so it works like a shared secret: store it in Kestra secrets, never in the flow YAML, and rotate it if the URL leaks.

The flow below receives GitHub webhook deliveries and verifies their HMAC signature before doing anything with the payload. The body is stored as received (`fetchType: STORE`), because the signature is computed over the raw bytes, not over re-serialized JSON.

```yaml
id: secure_webhook_handler
namespace: company.team.infra

triggers:
  - id: github_webhook
    type: io.kestra.plugin.core.trigger.Webhook
    key: "{{ secret('GITHUB_WEBHOOK_KEY') }}"
    fetchType: STORE

tasks:
  - id: validate_signature
    type: io.kestra.plugin.scripts.python.Script
    taskRunner:
      type: io.kestra.plugin.scripts.runner.docker.Docker
    containerImage: python:3.12-slim
    inputFiles:
      body.raw: "{{ trigger.uri }}"
    env:
      WEBHOOK_SECRET: "{{ secret('GITHUB_WEBHOOK_SECRET') }}"
      REQUEST_HEADERS: "{{ trigger.headers | toJson }}"
    script: |
      import hashlib, hmac, json, os, sys

      headers = {k.lower(): v for k, v in json.loads(os.environ["REQUEST_HEADERS"]).items()}
      received = (headers.get("x-hub-signature-256") or [""])[0]
      body = open("body.raw", "rb").read()
      expected = "sha256=" + hmac.new(os.environ["WEBHOOK_SECRET"].encode(), body, hashlib.sha256).hexdigest()

      if not hmac.compare_digest(expected, received):
          print("Signature mismatch, rejecting delivery")
          sys.exit(1)
      print("Signature valid")

  - id: process_payload
    type: io.kestra.plugin.core.log.Log
    message: "Valid delivery, payload stored at {{ trigger.uri }}"

errors:
  - id: alert_on_failure
    type: io.kestra.plugin.slack.notifications.SlackIncomingWebhook
    url: "{{ secret('SLACK_WEBHOOK_URL') }}"
    payload: |
      {"text": "Webhook delivery rejected or failed in {{ flow.id }} (execution {{ execution.id }})"}
```

### What This Flow Handles

*   **The URL:** It is built from the namespace, the flow id, and the `key` from Kestra secrets. Copy it from the Triggers tab into the GitHub webhook settings.
*   **Signature Check on Raw Bytes:** The script computes the HMAC-SHA256 of the stored body with the webhook secret and compares it in constant time with the `X-Hub-Signature-256` header. A mismatch fails the task and stops the flow before any processing.
*   **Fast Acknowledgement:** By default the trigger answers `200` as soon as the execution is created, which suits providers that expect a quick response. Set `wait: true` only if the caller must receive the flow's outputs.
*   **Audit Trail:** Every delivery, valid or rejected, is an execution with its logs, and failures reach Slack through the `errors` branch.

## Where Webhook URLs Pay Off

Webhook-driven automation fits many domains:

-   **CI/CD Pipeline Triggers:** Automatically start a build, test, or deployment workflow when code is pushed to a Git repository.
-   **Real-time Alerts and Notifications:** Ingest alerts from monitoring systems like PagerDuty or Grafana to trigger automated remediation runbooks.
-   **Data Synchronization:** Keep systems in sync by reacting to events like a new customer created in a CRM or a successful payment in Stripe.
-   **IoT Device Data Ingestion:** Provide a scalable endpoint for IoT devices to push sensor data for real-time processing and analysis.
-   **Microservice Communication:** Enable asynchronous, event-driven communication between services in a distributed architecture without tight coupling.
