This tutorial walks through a complete migration from Kestra 1.3 to 2.0. Every command and output shown here was captured from a real 1.3.5 → 2.0.0 run against a Kestra OSS instance backed by PostgreSQL.

:::alert{type="info"}
This tutorial covers **Kestra OSS running in standalone mode** (`server standalone`) on Docker Compose with a PostgreSQL backend. The flow migration steps apply equally to distributed and Helm deployments, but the server upgrade procedure differs. Enterprise Edition users must also run database migrations manually before starting the server; EE-specific steps are called out where they differ.
:::

:::alert{type="warning"}
This tutorial assumes you are already running **Kestra 1.3.x**. If you are on an older version, complete the required metadata migrations first: [KV Store and Secrets migration (1.1)](../../v1.1.0/kv-secrets-metadata-migration), [Namespace Files migration (1.2)](../../v1.2.0/namespace-file-migration), or the [LTS migration guide (1.0 to 1.3)](../../v1.3.0/lts-migration) if you are upgrading from 1.0.
:::

For a reference list of every breaking change, see the [2.0 migration index](../index.mdx).

## Prerequisites

- `kestra-migrate` binary on your `PATH`
- A backup of your Kestra PostgreSQL or H2 database
- `kestractl` v2 if you are on Enterprise Edition

## Step 1 — Export your flows

Export your flows from the 1.3 instance before making any changes to it.

```bash
curl -u "admin@kestra.io:yourpassword" \
  "http://localhost:8080/api/v1/flows/export/by-namespace?namespace=company.team" \
  -o company-team-flows.zip

unzip company-team-flows.zip -d ./flows/
```

Repeat for each namespace you want to migrate.

## Step 2 — Scan with `kestra-migrate --check`

Run the check against your exported flows:

```bash
kestra-migrate --check ./flows/
```

The examples below show output from eight flows that cover the main migration patterns. The first four show what `kestra-migrate` reports as `✔ v2-compatible` but does not rewrite — these are the dangerous false negatives. The last four show what it correctly detects and rewrites.

### Patterns `kestra-migrate` does not rewrite

**`flows/01-foreach.yaml`** — `ForEach` task, removed in 2.0:

```yaml
id: deploy-environments
namespace: company.migration

tasks:
  - id: deploy
    type: io.kestra.plugin.core.flow.ForEach
    values: '["dev", "staging", "production"]'
    tasks:
      - id: run_deploy
        type: io.kestra.plugin.core.log.Log
        message: "Deploying to {{ taskrun.value }} (step {{ taskrun.iteration }})"

      - id: verify
        type: io.kestra.plugin.core.log.Log
        message: "Health check passed for {{ taskrun.value }}"

  - id: done
    type: io.kestra.plugin.core.log.Log
    message: "All {{ outputs.deploy | length }} environments deployed"
```

**`flows/02-foreachitem-processor.yaml`** — subflow target for `ForEachItem`:

```yaml
id: process-report-item
namespace: company.migration

inputs:
  - id: item
    type: STRING

tasks:
  - id: process
    type: io.kestra.plugin.core.log.Log
    message: "Processing item: {{ inputs.item }}"
```

**`flows/03-foreachitem.yaml`** — `ForEachItem` task, removed in 2.0:

```yaml
id: process-report
namespace: company.migration

    description: CSV report to process, one row per line

tasks:
  - id: each_item

      rows: 1
    wait: true
    namespace: company.migration
```

### What `kestra-migrate` handles automatically

| Pattern | Before (1.3) | After (2.0) |
|---|---|---|
| Input type names | `BOOLEAN`, `ENUM` | `BOOL`, `SELECT` |
| State Store tasks | `io.kestra.plugin.core.state.*` | `io.kestra.plugin.core.kv.*` |
| Storage tasks | `io.kestra.plugin.core.storage.Purge` | `io.kestra.plugin.core.storage.PurgeExecutions` |
| Notifications | `io.kestra.plugin.notifications.slack.*` | `io.kestra.plugin.slack.notifications.*` |
| Task defaults key (step 1 of 2) | `taskDefaults:` | `pluginDefaults:` (also removed — see below) |
| Trigger conditions | `conditions: [DayWeekCondition, ...]` | `when: "{{ dayOfWeek(...) == ... }}"` |
| Flow trigger dependencies | `conditions: [ExecutionFlow, ...]` | `dependsOn: [{flowId: ...}]` |
| Debug task | `io.kestra.plugin.core.debug.Echo` | `io.kestra.plugin.core.log.Log` |
| Log Fetch | `io.kestra.plugin.core.log.Fetch` | `io.kestra.plugin.kestra.logs.Fetch` |
| Script runner key | `runner:` | `taskRunner:` |
| Required/defaults conflict | `required: false` + `defaults:` | Remove `required: false` |

### Removed task types

`kestra-migrate` flags these with `✗` warnings and writes the files through unchanged:

| Type | Replacement |
|---|---|
| `io.kestra.plugin.core.execution.Count` | Use a [KV Store](../../../concepts/kv-store) task or custom script |
| `io.kestra.plugin.core.execution.Resume` | Use the Kestra SDK |
| `io.kestra.plugin.core.trigger.Toggle` | Use the Kestra API or SDK |
| `io.kestra.plugin.git.Push` | `io.kestra.plugin.git.SyncFlows` |
| `io.kestra.plugin.scripts.nashorn.*` | Migrate to GraalJS or another script task |

### Parallel v1/v2 deployments

If you need migrated flows to run on a 1.3 instance while preparing for the 2.0 cutover, use `--stay-v1-compatible`. This skips the trigger `conditions` → `when` rewrite, which produces YAML that 1.3 cannot parse, and applies only backward-compatible changes:

```bash
kestra-migrate --stay-v1-compatible -o ./v2-flows-compat/ ./flows/
```

## Step 4 — Fix manual items

After `kestra-migrate`, grep for patterns the tool does not rewrite and fix them before importing to 2.0.

### `ForEach` and `ForEachItem`

```bash
grep -rn "plugin.core.flow.ForEach" ./v2-flows/
```

Both task types are removed in 2.0 and replaced by `Loop`. `kestra-migrate` gives them a `✔` and does not rewrite them.

**`ForEach` → `Loop`**

The minimum change is a type rename and expression rename:

```yaml
# Before (1.3) — ForEach
- id: deploy
  type: io.kestra.plugin.core.flow.ForEach
  values: '["dev", "staging", "production"]'
  tasks:
    - id: run_deploy
      type: io.kestra.plugin.core.log.Log
      message: "Deploying to {{ taskrun.value }} (step {{ taskrun.iteration }})"
```

```yaml
# After (2.0) — Loop
- id: deploy
  type: io.kestra.plugin.core.flow.Loop
  values: '["dev", "staging", "production"]'
  tasks:
    - id: run_deploy
      type: io.kestra.plugin.core.log.Log
      message: "Deploying to {{ item.value }} (step {{ item.index }})"
```

Expression changes:

| 1.3 | 2.0 |
|---|---|
| `{{ taskrun.value }}` | `{{ item.value }}` |
| `{{ taskrun.iteration }}` | `{{ item.index }}` |
| `{{ taskrun.key }}` | `{{ item.key }}` |
| `{{ outputs.loopTask \| length }}` | `{{ outputs.loopTask.iterationCount }}` |

The last row applies to expressions outside the loop that reference how many iterations ran, such as a downstream `Log` task summarizing the loop output.

**`ForEachItem` → `Loop` + `Subflow`**

`ForEachItem` dispatched batches of file rows to a separate subflow execution. In 2.0, use a `Loop` task with an inline `Subflow` task:

```yaml
# Before (1.3) — ForEachItem
- id: each_item
  type: io.kestra.plugin.core.flow.ForEachItem
  items: "{{ inputs.report_file }}"
  batch:
    rows: 1
  wait: true
  namespace: company.migration
  flowId: process-report-item
  inputs:
    item: "{{ taskrun.items }}"
```

```yaml
# After (2.0) — Loop + Subflow
- id: each_item
  type: io.kestra.plugin.core.flow.Loop
  values: "{{ inputs.report_items }}"
  tasks:
    - id: process_item
      type: io.kestra.plugin.core.flow.Subflow
      namespace: company.migration
      flowId: process-report-item
      inputs:
        item: "{{ item.value }}"
      wait: true
```

:::alert{type="info"}
The `Loop` task iterates over a list of values, not a file directly. If your `ForEachItem` flow used a `FILE` input, you will need to read and parse the file first — for example with a script task — and pass the resulting list to `Loop` via `values`. See the [ForEach and ForEachItem replaced by Loop](../foreach-loop/index.md) guide for a complete worked example of this pattern.
:::

### `pluginDefaults` at flow level

Flow-level `pluginDefaults` is removed in 2.0. `kestra-migrate` gives it a `✔` and does not rewrite it. Grep for it in your output directory:

```bash
grep -rn "pluginDefaults:" ./v2-flows/
```

Any match requires manual work before the flow will behave correctly on 2.0. There is no automatic migration path: you must copy every property from the `pluginDefaults` block onto each individual task that needs it. If you skip this step, the tasks run without those values. Shared headers, timeouts, credentials, or method settings are simply not applied, and the flow produces different results than it did on 1.3.

The flow editor shows a `1 Error(s)` badge with `Validation error: Unrecognized field "pluginDefaults"`. Flows already in the database from before the upgrade can still execute, but the defaults are dropped. Fresh imports via the API return HTTP 422.

**OSS: inline the values on each task:**

```yaml
# Before (1.3) — shared pluginDefaults
pluginDefaults:
  - type: io.kestra.plugin.core.http.Request
    values:
      method: GET
      headers:
        Accept: application/json
        X-API-Version: "2"
      options:
        connectTimeout: PT5S
        readTimeout: PT30S

tasks:
  - id: fetch_orders
    type: io.kestra.plugin.core.http.Request
    uri: https://example.com/api/orders

  - id: fetch_products
    type: io.kestra.plugin.core.http.Request
    uri: https://example.com/api/products
```

```yaml
# After (2.0, OSS) — inline on each task
tasks:
  - id: fetch_orders
    type: io.kestra.plugin.core.http.Request
    uri: https://example.com/api/orders
    method: GET
    headers:
      Accept: application/json
      X-API-Version: "2"
    options:
      connectTimeout: PT5S
      readTimeout: PT30S

  - id: fetch_products
    type: io.kestra.plugin.core.http.Request
    uri: https://example.com/api/products
    method: GET
    headers:
      Accept: application/json
      X-API-Version: "2"
    options:
      connectTimeout: PT5S
      readTimeout: PT30S
```

**EE: move defaults to a namespace Policy:**

See [Plugin defaults removed](../plugin-defaults-removed/index.md) for the Policy syntax.

### `taskDefaults` → `pluginDefaults` is a two-step migration

`kestra-migrate` renames `taskDefaults:` to `pluginDefaults:` in flow 07. Both keys are rejected with a 422 on the 2.0 server:

```
# taskDefaults: (original 1.3 key)
HTTP 422 {"detail":"Unrecognized field \"taskDefaults\""}

# pluginDefaults: (kestra-migrate output)
HTTP 422 {"detail":"Unrecognized field \"pluginDefaults\""}
```

After `kestra-migrate` runs, grep for `pluginDefaults:` in your output and inline the values or migrate to a Policy as described above.

### Other patterns to grep for

```bash
# Removed Pebble function
grep -rn "json(" ./v2-flows/
grep -rn "| json" ./v2-flows/

# Script task runner rename
grep -rn "^\s*runner:" ./v2-flows/
```

| 1.3 | 2.0 | Guide |
|---|---|---|
| `{{ json(outputs.task.body).key }}` | `{{ fromJson(outputs.task.body).key }}` | [json() function removed](../json-function-removed/index.md) |
| `{{ value \| json }}` | `{{ value \| toJson }}` | [json() function removed](../json-function-removed/index.md) |
| `runner: type: ...Docker` | `taskRunner: type: ...Docker` | — |

## Step 5 — Switch to Kestra 2.0

Stop the Kestra container (leave Postgres running):

```bash
docker compose stop kestra
```

Update `docker-compose.yml`:

```yaml
# Image
image: kestra/kestra:v2.0.0-slim

# Auth config key changed from camelCase to kebab-case in 2.0
kestra:
  server:
    basic-auth:          # was: basicAuth
      enabled: true
      username: admin@kestra.io
      password: "Kestra123!"
```

Start the 2.0 container:

```bash
docker compose up kestra -d
```

:::alert{type="warning"}
The plugin auto-install migration (`2.0.11`) detects `io.kestra.plugin.core.flow.ForEach` and `io.kestra.plugin.core.flow.ForEachItem` as "missing types" and attempts to install plugins for them.       'InvalidTypeConstraintViolationException: Invalid type: io.kestra.plugin.core.flow.ForEachItem'

These flows need to be rewritten before they can run on 2.0.
:::

### Database migration on Enterprise Edition

On EE, the server refuses to start if pending migrations exist. Run them manually before starting:

```bash
# Check pending
kestra migrate plan

# Apply
kestra migrate run
```

In Docker Compose, run migrations as a one-time service before starting the main server:

```yaml
services:
  kestra-migrate:
    image: kestra/kestra-ee:v2.0.0
    command: migrate run
    environment:
      KESTRA_CONFIGURATION: |
        # same as your kestra service config
    depends_on:
      postgres:
        condition: service_healthy

  kestra:
    image: kestra/kestra-ee:v2.0.0
    depends_on:
      kestra-migrate:
        condition: service_completed_successfully
```

See [Database migrations](../database-migrations/index.md) for the full EE reference.

## Troubleshooting

**`kestra-migrate` exits 1 when I expected 0**
The tool exits `1` if any flow needs migration in `--check` mode, or has unrewritable types in both modes. Check the output for `✎` (needs rewrite) and `✗` (removed type) markers.

**A flow passes `kestra-migrate` but fails to import on 2.0**
Run these checks against your output directory:

```bash
grep -rn "plugin.core.flow.ForEach" ./v2-flows/
grep -rn "plugin.core.flow.ForEachItem" ./v2-flows/
grep -rn "pluginDefaults:" ./v2-flows/
grep -rn "json(" ./v2-flows/
grep -rn "| json" ./v2-flows/
grep -rn "^\s*runner:" ./v2-flows/
```

**The trigger `when` expression ANDs multiple day conditions**
`kestra-migrate` joins multiple `DayWeekCondition` entries with `and`, which means the trigger would only fire if the date is simultaneously Monday, Wednesday, and Friday. Rewrite manually with `or`:

```yaml
when: >
  {{ (dayOfWeek(trigger.date) == 'MONDAY') or
     (dayOfWeek(trigger.date) == 'WEDNESDAY') or
     (dayOfWeek(trigger.date) == 'FRIDAY') }}
```

See [Trigger conditions redesign](../trigger-conditions-redesign/index.md) for the complete `when` expression reference.

**Login fails after upgrading to 2.0**
The `basicAuth:` config key changed to `basic-auth:` (kebab-case) in 2.0. Update your `KESTRA_CONFIGURATION` or `application.yaml` before starting the 2.0 server.

**EE server refuses to start after upgrade**
If you see `Pending migrations exist, server startup blocked`, run `kestra migrate run` before starting the server. See [Database migrations](../database-migrations/index.md).

**`pluginDefaults` flows execute but behavior changed**
If a flow ran correctly on 1.3 but produces different results on 2.0, check whether it used `pluginDefaults`. The 2.0 server drops the block and the flow editor shows a `1 Error(s)` badge, but DB-migrated flows can still execute without the defaults applied. Verify with the API: `GET /api/v1/flows/{namespace}/{id}`. If `pluginDefaults` is absent from the response, inline the values on each task (OSS) or migrate to a namespace Policy (EE).
