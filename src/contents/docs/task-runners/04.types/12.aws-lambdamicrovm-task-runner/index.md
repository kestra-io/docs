Run tasks natively on AWS Lambda MicroVMs — no container runtime required, with built-in image management and S3-based file staging.

## When to use the Lambda MicroVM task runner

Use the Lambda MicroVM task runner when your workload needs lightweight VM isolation on ARM64 without the overhead of container scheduling or EC2 instance provisioning:

- **Fast-start serverless workloads** that need VM-level isolation but can tolerate a one-time per-region image build (a few minutes on first run)
- **Long-running non-containerized tasks** that exceed Lambda's 15-minute function timeout — runs can last up to 8 hours
- **ARM64-native workloads** built for Amazon Linux 2023 on ARM64 that do not require a custom container image
- **Simplified IAM setup** where you want the runner to manage image builds automatically without maintaining AMIs or job queues

For containerized workloads, use the [AWS Batch task runner](../04.aws-batch-task-runner/index.md). For direct EC2 control with Spot instances, GPU support, or custom AMIs, use the [AWS EC2 task runner](../05.aws-ec2-task-runner/index.md).

:::alert{type="warning"}
This runner is **ARM64 only**. The `containerImage` property is ignored — the runner builds and manages its own Amazon Linux 2023 ARM64 base image. Do not set `containerImage` on tasks using this runner.
:::

## How it works

For each task run, the Lambda MicroVM task runner:

1. On the **first run** (per unique bucket and region combination), builds a managed ARM64 image named `kestra-task-runner-<hash>` from an Amazon Linux 2023 minimal base. This one-time build takes a few minutes. Subsequent runs reuse the cached image.
2. Uploads `inputFiles` and `namespaceFiles` to S3 under the `kestra-lambda-microvm/` prefix using presigned URLs — the MicroVM requires no IAM credentials for staging.
3. Starts the MicroVM and runs the task's commands directly on the instance OS.
4. Streams command output to the log group at `/aws/lambda-microvm/kestra` (default) via CloudWatch Logs.
5. Downloads `outputFiles` from S3 to Kestra internal storage once the command completes.
6. Terminates the MicroVM unconditionally on success, failure, or worker interruption.

The MicroVM accesses S3 via presigned URLs generated by the Kestra worker, so the execution role does not need S3 permissions for file staging.

The following Pebble expressions and environment variables are available inside the task:

| Pebble expression | Environment variable | Description |
|---|---|---|
| `{{ workingDir }}` | `WORKING_DIR` | Path to the task's working directory on the instance where input files are placed |
| `{{ outputDir }}` | `OUTPUT_DIR` | Path to the output directory; all files written here are automatically captured |
| `{{ bucketPath }}` | `BUCKET_PATH` | S3 URI of the task's staging folder in the configured bucket |

:::alert{type="info"}
If a run fails, look up the failure detail in `{{ outputs.<taskId>.vars.kestraTaskRunner }}`. This output includes the MicroVM identifier and any error message from the run.
:::

## IAM permissions

The Lambda MicroVM task runner uses two IAM roles: a **runner credential** role (used by the Kestra worker to submit and monitor runs) and two dedicated roles for the MicroVM itself — a **build role** (for image construction) and an **execution role** (for the task at runtime).

### Runner credentials

The IAM principal used by Kestra (the user or role whose credentials are passed via `accessKeyId`/`secretKeyId`, or the worker's instance profile) needs the following minimum permissions:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "lambda:RunMicrovm",
        "lambda:GetMicrovm",
        "lambda:TerminateMicrovm",
        "lambda:CreateMicrovmImage",
        "lambda:GetMicrovmImage",
        "lambda:ListMicrovmImages",
        "lambda:GetMicrovmImageVersion",
        "lambda:ListManagedMicrovmImages",
        "lambda:ListManagedMicrovmImageVersions",
        "lambda:TagResource",
        "lambda:PassNetworkConnector"
      ],
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:ListBucket"
      ],
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "logs:DescribeLogGroups",
        "logs:CreateLogGroup",
        "logs:FilterLogEvents"
      ],
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "iam:PassRole"
      ],
      "Resource": [
        "<buildRoleArn>",
        "<executionRoleArn>"
      ]
    }
  ]
}
```

Replace `<buildRoleArn>` and `<executionRoleArn>` with the ARNs of the two roles described below.

:::alert{type="info"}
**Running on Kestra Cloud?** The Cloud control plane runs outside your AWS account and has no EC2 instance profile to supply a base AWS identity. Static `accessKeyId` / `secretKeyId` credentials are required.
:::

### Build role

The build role is assumed by Lambda MicroVM to construct the managed image on first run. Create a role with the following trust policy and permissions:

**Trust policy:**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "lambda.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

**Permissions:**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::<bucket>/kestra-lambda-microvm/bootstrap/*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      "Resource": "*"
    }
  ]
}
```

Replace `<bucket>` with your staging bucket name.

### Execution role

The execution role is assumed by the MicroVM at runtime when running your task commands. At minimum it needs permission to write logs:

**Trust policy:**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "lambda.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

**Permissions:**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      "Resource": "*"
    }
  ]
}
```

Add any permissions your task commands need (for example, S3, DynamoDB, or other AWS service access) to this role.

### KMS-encrypted buckets

If your S3 bucket uses a customer-managed KMS key for server-side encryption, set `kmsKeyId` on the task runner and add the following to both the build role and execution role:

```json
{
  "Effect": "Allow",
  "Action": [
    "kms:GenerateDataKey",
    "kms:Decrypt"
  ],
  "Resource": "<kmsKeyArn>"
}
```

### S3 lifecycle rule

The runner stages files under `kestra-lambda-microvm/run/` in your bucket. Add a lifecycle rule to expire objects under this prefix after 1 day to avoid accumulating staging objects from completed runs.

## Example flows

### Basic shell command

```yaml
id: lambda_microvm_shell
namespace: company.team

tasks:
  - id: shell
    type: io.kestra.plugin.scripts.shell.Commands
    taskRunner:
      type: io.kestra.plugin.ee.aws.runner.LambdaMicroVm
      region: us-east-1
      bucket: my-kestra-staging-bucket
      buildRoleArn: "arn:aws:iam::123456789012:role/kestra-lambda-build-role"
      executionRoleArn: "arn:aws:iam::123456789012:role/kestra-lambda-execution-role"
    commands:
      - echo "Hello from Lambda MicroVM"
```

### Input and output files

```yaml
id: lambda_microvm_with_files
namespace: company.team

inputs:
  - id: file
    type: FILE

tasks:
  - id: process
    type: io.kestra.plugin.scripts.shell.Commands
    inputFiles:
      data.txt: "{{ inputs.file }}"
    outputFiles:
      - out.txt
    taskRunner:
      type: io.kestra.plugin.ee.aws.runner.LambdaMicroVm
      region: us-east-1
      bucket: my-kestra-staging-bucket
      buildRoleArn: "arn:aws:iam::123456789012:role/kestra-lambda-build-role"
      executionRoleArn: "arn:aws:iam::123456789012:role/kestra-lambda-execution-role"
      memory: 4096
    commands:
      - cp "{{ workingDir }}/data.txt" "{{ workingDir }}/out.txt"
```

### With STS role assumption

Instead of static `accessKeyId` / `secretKeyId` credentials, authenticate via AWS STS `AssumeRole`:

```yaml
id: lambda_microvm_sts
namespace: company.team

tasks:
  - id: shell
    type: io.kestra.plugin.scripts.shell.Commands
    taskRunner:
      type: io.kestra.plugin.ee.aws.runner.LambdaMicroVm
      region: us-east-1
      bucket: my-kestra-staging-bucket
      buildRoleArn: "arn:aws:iam::123456789012:role/kestra-lambda-build-role"
      executionRoleArn: "arn:aws:iam::123456789012:role/kestra-lambda-execution-role"
      stsRoleArn: "arn:aws:iam::123456789012:role/kestra-runner-role"
      stsRoleExternalId: "{{ secret('STS_EXTERNAL_ID') }}"
      stsRoleSessionName: kestra-session
    commands:
      - echo "Hello from Lambda MicroVM with STS"
```

:::alert{type="warning"}
**This example is keyless only when Kestra runs inside AWS.** On a self-hosted instance on EC2 or EKS, the AWS SDK uses the instance profile or IRSA to make the `sts:AssumeRole` call without static keys. On Kestra Cloud, you must supply `accessKeyId` and `secretKeyId` alongside `stsRoleArn`.
:::

## Security

:::alert{type="warning"}
The MicroVM communicates with the Kestra worker over an unauthenticated webhook connection. Do not expose port `8080` on the Kestra worker to untrusted networks when using this runner.
:::

Use `ingressNetworkConnectors` and `egressNetworkConnectors` to control network access for the MicroVM when your account has Lambda Network Connectors configured.

## Monitoring

Set `monitoring.enabled: true` to run the task command under [kotlp](https://github.com/kestra-io/kotlp), a portable observability wrapper Kestra stages into the task's working directory. No image change is needed.

kotlp reports the instance's resource usage as `process.*` task metrics, sampled every `monitoring.metricsInterval` (default `PT1S`):

| Metric | Type | Unit | Attribute |
|---|---|---|---|
| `process.cpu.time` | sum | `s` | `cpu.mode`: `user` or `system` |
| `process.cpu.utilization` | gauge | `1` | `cpu.mode`: `user` or `system` |
| `process.memory.usage` | gauge | `By` | — |
| `process.memory.virtual` | gauge | `By` | — |
| `process.disk.io` | sum | `By` | `disk.io.direction`: `read` or `write` |
| `process.network.io` | sum | `By` | `network.io.direction`: `receive` or `transmit` |
| `process.thread.count` | gauge | `{thread}` | — |
| `process.open_file_descriptor.count` | gauge | `{count}` | — |

The three sum metrics (`process.cpu.time`, `process.disk.io`, `process.network.io`) are cumulative and reflect totals for the entire run. The gauge metrics reflect the last sample taken before the command exits, not a peak.

kotlp also runs an embedded OTLP receiver, so traces the command exports are captured as task traces.

```yaml
id: lambda_microvm_with_monitoring
namespace: company.team

tasks:
  - id: run
    type: io.kestra.plugin.scripts.shell.Commands
    taskRunner:
      type: io.kestra.plugin.ee.aws.runner.LambdaMicroVm
      region: us-east-1
      bucket: my-kestra-staging-bucket
      buildRoleArn: "arn:aws:iam::123456789012:role/kestra-lambda-build-role"
      executionRoleArn: "arn:aws:iam::123456789012:role/kestra-lambda-execution-role"
      monitoring:
        enabled: true
    commands:
      - echo "stdout line"
      - echo "stderr line" >&2
```

| Property | Default | Description |
|---|---|---|
| `monitoring.enabled` | `false` | When `true`, wraps the task command with kotlp. |
| `monitoring.metricsInterval` | `PT1S` | How often kotlp samples resource usage. Accepts values between `PT0.001S` and `PT1H`. |

### Monitoring constraints

Two requirements apply when monitoring is enabled:

- `bucket` must be configured. kotlp is staged alongside other input files. The task fails immediately if `bucket` is absent.
- An explicit `commands` list is required. kotlp wraps the command you supply; it cannot wrap an image entrypoint.

## Key properties

| Property | Required | Default | Description |
|---|---|---|---|
| `region` | Yes | — | AWS region where the MicroVM runs. |
| `bucket` | Yes | — | S3 bucket for file staging and bootstrap objects. |
| `buildRoleArn` | Yes | — | ARN of the IAM role Lambda MicroVM assumes to build the managed image. See [Build role](#build-role). |
| `executionRoleArn` | Yes | — | ARN of the IAM role the MicroVM assumes at runtime. See [Execution role](#execution-role). |
| `memory` | No | — | MicroVM memory in MiB. |
| `serverSideEncryption` | No | `AES256` | S3 server-side encryption algorithm. Set to `aws:kms` when using a KMS key. |
| `kmsKeyId` | No | — | KMS key ID or ARN for S3 object encryption. Requires `serverSideEncryption: aws:kms`. |
| `accessKeyId` | No | — | AWS access key ID. Uses the worker's instance profile when omitted. |
| `secretKeyId` | No | — | AWS secret access key. |
| `sessionToken` | No | — | AWS session token for temporary credentials. |
| `stsRoleArn` | No | — | ARN of an IAM role to assume via STS. |
| `stsRoleExternalId` | No | — | External ID for the STS trust policy. |
| `stsRoleSessionName` | No | — | Name tag for the assumed-role session. |
| `endpointOverride` | No | — | Override the AWS endpoint URL (useful in GovCloud or LocalStack). |
| `waitUntilCompletion` | No | `PT1H` | Maximum time to wait for the run to finish. Cannot exceed `PT8H`; values over 8 hours are rejected. |
| `completionCheckInterval` | No | `PT5S` | How often to poll for run completion. |
| `logGroup` | No | `/aws/lambda-microvm/kestra` | CloudWatch Logs log group for task output. |
| `imageIdentifier` | No | — | Custom image identifier. Leave unset to use the Kestra-managed image. |
| `syncWorkingDirectory` | No | `false` | When `true`, syncs the entire working directory back to S3 after the run completes. |
| `idlePolicy` | No | — | Policy controlling MicroVM idle behavior. |
| `ingressNetworkConnectors` | No | — | Lambda Network Connectors for inbound network access. |
| `egressNetworkConnectors` | No | — | Lambda Network Connectors for outbound network access. |
| `tags` | No | — | Tags to apply to MicroVM resources. |

For the full property reference, see the [plugin documentation](/plugins/plugin-ee-aws/aws-task-runners/io.kestra.plugin.ee.aws.runner.lambdamicrovm).
